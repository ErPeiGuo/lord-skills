# Verify AI use of knowledge

Choose checks by the changed responsibility. A small clarification needs its affected routes checked; a new root or substantial restructuring needs representative questions across its actual scope. Reuse valid results for unchanged inputs.

## Structure and semantics

Use the project's existing checker when available. Check changed links and anchors, reachable owners, current status and incoming routes. Read affected passages for contradictions, duplicate authority, omitted conditions, proposals presented as approval, and targets presented as implemented results. Link existence and metadata validity do not establish factual truth.

Do not create a checker or a new reporting system just to perform this review. Use ordinary file tools for a bounded manual check when no suitable checker exists.

## Retrieval and recovery

Select actual questions the next AI will need to answer. Cover the relevant subset:

- What is approved, excluded or unresolved, and why?
- Which owner defines a shared rule or dependency?
- What is implemented or verified, and where is the supporting evidence?
- What must happen next after context loss?
- Can a local change be understood without loading unrelated domains?

Start from the declared entrypoint and follow the actual route. Retain a compact `question -> paths/sections read -> answer or gap -> stop reason` only in the existing task/evidence record or current response. Do not duplicate the source answer in another maintained catalog.

For a new root or material routing redesign, use a fresh-context read-only agent when available and authorized. Give it questions, entrypoint, allowed scope and necessary project instructions; withhold expected answers and prior chat. Check the actual answer and source passage. A self-check is still useful when independent execution is unavailable; label it accurately. Do not dispatch one reviewer per leaf or restart a completed audit.

Repair routes when the AI cannot find the owner, reads unrelated material, loses a necessary condition or confuses target with observation. Fix the demonstrated cause and rerun the affected questions. Do not add search infrastructure until recurring retrieval failures establish a need.

## Before implementation

Check that the approved scope supplies the important behaviors, constraints, dependencies, failure outcomes and acceptance conditions needed for the requested implementation. Unresolved core choices remain visible; ordinary coding details do not need advance approval. Perform the applicable project review without creating an extra universal approval stage.

After implementation, update affected knowledge using actual source and verification evidence. Distinguish passed, failed, skipped and unverified checks. Finish when the requested checks have succeeded or the concrete unresolved scope has been reported; no fixed number of review rounds is required.
