# Maintain project knowledge

Select the section matching the task. These operations share the ownership and evidence rules in the skill entrypoint; they do not require separate workflow invocations.

## Initialize or extend

Inspect existing instructions, routes and relevant knowledge before creating another root. Reuse the selected project's structure. If no root exists, create a short entrypoint and only the subject pages justified by available content. Add a compact current-work record when there is resumable work; do not pre-create empty requirement, design, test or archive trees.

The entrypoint identifies the subject, scope and routes. Each leaf makes its purpose, applicability and knowledge status explicit. Reuse metadata conventions; add stable IDs, summaries or reading conditions when they help actual routing or cross-references. Do not impose a mandatory metadata schema on every project.

Separate approved targets from proposals and source-backed observations even when they share a small page. Existing implementation can establish current behavior, not approval of that behavior. Preserve useful original inputs as references when traceability needs them, with an explicit route to the adopted meaning. A source dump is not a second live specification.

## Capture during discussion

After each important confirmation, update its canonical owner before continuing discussion that depends on it. Retain the current decision, necessary reason, applicability, material consequence and still-effective rejected alternative. Do not wait for final drafting or a compaction warning; ordinary user confirmation is enough to perform an authorized writeback.

Label unresolved proposals and questions explicitly. Capture enough context to resume a substantive unresolved choice, without preserving brainstorming transcripts. Do not convert a suggestion, reference behavior or agent preference into approved scope. Reuse confirmations already present in the conversation or authoritative documents.

Keep current reasoning when replacing a decision. Remove the superseded prescription from the live contract; keep an old value only if it still describes an actual implementation or another applicable scope, labelled accordingly. Version control normally retains prior versions. Maintain separate historical records only for an actual traceability requirement; do not introduce a decision chronology into current facts by default.

## Apply a change

Reread the owner immediately before editing. Update the whole affected claim, including its conditions, consequences and necessary reason. Follow known dependencies and scoped incoming references to repair stale links or competing summaries. Preserve concurrent edits and unrelated subjects.

Verify implementation claims against the named source, tests, configuration or runtime evidence as needed. Keep a changed target and an unchanged implementation distinct. Never mark a new target implemented, tested or accepted because its document was updated. Evidence should identify the object, relevant baseline, observation and meaningful limits; do not copy complete logs or refresh dates without checking the claims.

Update only the directly affected knowledge and routes. Do not create a second task ledger, permanent audit report, full source inventory or duplicate schema merely to document the update. A structural change needs a concrete retrieval, ownership or maintenance problem to solve.

## Resume or hand off

Read the entrypoint, current-work pointer and relevant owners. Recover the current objective, effective constraints and reasons, unresolved choices, implementation/verification state and next action. Ask only for a material gap that those sources cannot resolve; do not repeat settled questions.

Persist changed knowledge and a useful resume pointer before handoff. The work record owns progress, blockers and next action, and links to domain rules rather than repeating them. Use an existing state or task owner; add one only if none can hold the necessary continuation. Retire redundant completed process material after its useful facts and evidence have a durable owner and incoming links are repaired.

If writing fails or the target is read-only, state what remains unpersisted and the concrete next recovery action. Do not claim that chat text or an automatic memory summary has updated the project files.
